## Scope decision

The dataset also offers closed-year files for 2016–2024 and per-district files.
They were **excluded**. Two reasons:

1. None of the twelve business questions needs history before 2025.
2. The chosen scope has a property the analysis depends on — a request submitted
   on or after 2025-01-01 must be either still open, closed in 2025, or closed in
   2026, so **every submission month from January 2025 is completely covered**.
   That is what makes the year-over-year demand comparison defensible. Adding
   partial older years would not extend that guarantee.

`scripts/download_data.py --all-closed` retrieves the full set if needed.

## Snapshot date

**2026-08-09**, derived from the data rather than assumed.

For active records the published `case_age_days` equals *(extract date − request
date)*, so the extract date is recoverable as the modal value of
`date_requested + case_age_days`. It agrees for
**99.63%** of active records
(81,061 of them). See audit check DQ-03.

## Fields excluded from every output

Although the source is public, these fields are dropped before anything is
written to disk. See [`07_methodology/methodology.md`](../07_methodology/methodology.md) §9.

| Field | Reason |
|---|---|
| `public_description` | Resident-submitted free text |
| `street_address` | Exact point address |
| `lat`, `lng` | Exact coordinates; geography is published at district / community / ZIP |
| `referred` (raw text) | Contains staff and vendor email addresses; normalized to a destination label |
| `iamfloc`, `floc` | Internal asset identifiers, no analytical value here |
| `sap_notification_number` | Internal system identifier |

## Caveats carried from the source

The City states, and this project repeats wherever a conclusion is drawn:

> This data includes every user-submitted report and should not be considered an
> official record of City maintenance work. This data does not include details
> about any work performed to fix a problem or the date and time work was completed.

Additional conditions found by this project's own audit — dual semantics in
`case_age_days`, an unstable service taxonomy, cross-file duplicate ids — are
quantified in [`02_data_audit/data_quality_report.md`](../02_data_audit/data_quality_report.md).
